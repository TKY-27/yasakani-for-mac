The user is asking for a complete Python 3.11 package for a deterministic async job runner. Requirements:

1. Read a JSON manifest
2. Enforce only one active GPU job
3. Persist atomic state
4. Resume completed work
5. Stream structured JSONL events
6. Handle SIGINT
7. Mask configured secrets (redact)
8. pytest tests: success, failure, cancellation, resume
9. Present all source files in separate fenced blocks with their paths
10. Include pyproject.toml

Let's design this carefully.

Let's think about the semantics:

### Manifest (JSON)
```json
{
  "version": 1,
  "run_id": "run-2024-05-01-a",
  "workspace": "./workspace",
  "secrets": {
    "api_key": {"source": "env", "name": "MY_API_KEY"},
    "token": {"value": "literal-secret"}
  },
  "jobs": [
    {
      "id": "train-1",
      "kind": "gpu",
      "command": ["python", "train.py", "--secret", "{{api_key}}"],
      "depends_on": [],
      "retries": 2
    },
    {"id": "log", "kind": "cpu", "command": ["python", "-c", "print('ok')"]}
  ]
}
```

The runner needs to be deterministic. Determinism: schedule jobs by deterministic ordering (topological, tiebreak by job ID), fixed seeds, no wall-clock dependence on ordering, fixed concurrency for CPU jobs.

### One active GPU job
Implement an `AsyncBoundedSemaphore(1)`-style exclusive lock for GPU work: GPU jobs run one at a time; concurrent attempts are queued. Should also enforce at the process level? "Enforce one active GPU job" — simplest interpretation: only one GPU job may be running at any point (within the process); use asyncio.Lock, or better, a dedicated GPU worker task (single consumer) that pulls GPU jobs off a queue. This guarantees only one active GPU job. The scheduler dispatches CPU jobs to a pool and GPU jobs to a single GPU worker.

Actually, to be robust and testable, let's implement a `GpuLock` that hands out a slot via an `asyncio.Queue(1)` or `asyncio.Semaphore(1)`. A dedicated GPU pipeline: scheduler enqueues GPU jobs; a single GPU worker task processes them serially. This makes it trivial to enforce "one active GPU job" and is deterministic.

### Atomic state persistence
State file `workspace/state.json` (or `state/` directory). Atomic write: write to a temp file in the same directory, `fsync`, `os.replace` (atomic on POSIX). Also persist a sequence number for events. Save state after each transition (job_started, job_succeeded, job_failed, run finished). Use a `StateStore` with `load()` and `save()`.

State schema:
```json
{
  "version": 1,
  "run_id": "...",
  "status": "running" | "succeeded" | "failed" | "cancelled",
  "jobs": {"job-id": {"status": "pending"|"running"|"succeeded"|"failed"|"skipped", "attempt": 0, ...}}
}
```

### Resume
On startup, if state exists and run_id matches, jobs marked `succeeded`/`failed-final` (per retry exhaustion or `fail_fast`) are considered completed: resume = skip succeeded jobs (their outputs are reused), re-run pending ones, and restart retryable failed jobs? Simpler and deterministic: resume skips `succeeded` jobs and runs everything else; downstream jobs of skipped ones proceed if all dependencies succeeded.

### JSONL events
Event file `workspace/events.jsonl`. Each event: `{"seq": n, "event": "...", "ts": ...}` — but determinism: avoid wall-clock timestamps, or include them but don't affect ordering. Better: include a monotonically increasing `seq`, `event` type, and payload. For structured JSONL, each line is a JSON object. Write with flush after each event; events go through a single event bus to serialize writes (asyncio lock / dedicated writer task). Deterministic ordering: since the scheduler is mostly deterministic, events are emitted from a single-writer task fed by an asyncio.Queue, and `seq` increments per event.

Event kinds:
- `run_started`
- `job_queued` (maybe unnecessary)
- `job_started` {job_id, attempt, kind, command? masked}
- `job_succeeded` {job_id, duration?}
- `job_failed` {job_id, attempt, exit_code}
- `job_skipped` (due to cancellation)
- `run_succeeded` / `run_failed` / `run_cancelled`
- `state_saved` (maybe)
- `secret_redacted`? nah.

### SIGINT
The CLI installs a signal handler via `loop.add_signal_handler(signal.SIGINT, ...)` which sets a cancellation request; the scheduler catches it and performs a graceful shutdown: mark the current job as being cancelled, wait for the running job to be cancelled (or wait for it to finish? For deterministic tests, immediate cancel is simpler). Approach: on SIGINT, if the run is not already cancelling, set a `_cancelling` flag, `cancel` the top-level `run` task, catch the `CancelledError` in the scheduler, save state with status `cancelled` (record per-job statuses), emit `run_cancelled`, and exit with code 130 (SIGINT convention). A second SIGINT during shutdown → force-kill (`os._exit` or raise). In tests, instead of sending a real signal (hard in pytest), we can directly invoke the runner's `request_cancel()`; but the requirement says "handle SIGINT" — we'll implement the handler in the CLI and also make it unit-testable: `run_with_signal_handlers` uses `loop.add_signal_handler` only when available (main thread). In tests, we can simulate SIGINT by calling `runner.request_cancel()`, and additionally test the handler wiring with a fake loop? Simpler: expose `install_signal_handlers(loop, runner)` which adds the handler, and in a test, use `asyncio.get_running_loop().add_signal_handler` in-process to send SIGINT to our own process via `os.kill(os.getpid(), SIGINT)`... that could affect pytest itself; but the signal is handled by the loop so it's fine. In CI on Windows `add_signal_handler` may not be available; guard with `hasattr`.

Design: `JobRunner.request_cancel(reason="sigint")` → sets a flag and cancels the tasks. The scheduler's `run()` catches `asyncio.CancelledError`, finalizes state (`status: cancelled`), and emits `run_cancelled`.

Also treat SIGINT as cancellation: exit code 130.

### Secret redaction
The manifest defines `secrets` — either literal values or env-var sources. Jobs reference them with `{{secret_name}}` in their command. Redaction: all events (and logs) must replace any occurrence of a secret value with `"[REDACTED]"`. The secret values themselves must not appear in the manifest's command? Actually the manifest substitutes the placeholder to the real value before exec (the subprocess needs it). But events containing stdout, error messages, or the command line get redacted: run `redact(text)` replacing each known secret value with `[REDACTED]` before writing an event. Also, to avoid leaking the command line, we store `argv` in events with placeholders rather than the substituted values (i.e., keep `{{secret}}` in recorded commands). Deterministic.

Redactor: holds a list of secret values (strings), applies `text.replace(value, "[REDACTED]")`. Edge case: empty secret value → skip. Sort values by descending length for consistent replacement.

### Job execution
Jobs are subprocess commands: `command: [args]`, optional `env` (values may contain placeholders), optional `cwd` (default workspace), optional `timeout` seconds. Determinism: no wall-clock in state (durations in events are fine? To keep it deterministic, avoid durations in state; in events, we might omit wall-clock or include `seq` only. "Stream structured JSONL events" — we might include `ts` as logical clock `seq`. To keep output byte-deterministic, skip wall-clock timestamps, or include but only seq. Let's include `seq` and `event`; that's it.)

Exit code 0 → success; non-zero → failure; timeout → cancel → failure with a special reason; cancellation → skipped/failed with reason cancelled.

Retries: `retries: N` means total attempts = N+1? Let's define `max_attempts` (default 1). Deterministic retry: fixed backoff, but to be fully deterministic in tests, we make it immediate (no delay) or a configurable `retry_delay` (default 0). Let's do `retries` and an optional `retry_delay` float (default 0.0).

Fail-fast: on final failure of a job, mark the remaining pending jobs with unsatisfied deps as `skipped` (reason `upstream_failure`). Run status `failed`.

### Determinism
- Job scheduling: a ready queue is a min-heap with deterministic priority: (topological generation? or just sorted job ID, or manifest order). Use manifest index as tiebreaker: a ready queue is a sorted list of (manifest_index) — deterministic. Ready set is computed by a deterministic iteration of jobs in manifest order, so first-ready-first-run.
- CPU jobs run with a bounded pool `cpu_concurrency` (default e.g. 4). GPU jobs serial via the single worker.
- Event sequence numbers assigned when enqueued into a single-writer queue.
