Part One: Operational Boundaries.
The system serves only one active request at a time, and all model state is owned exclusively by a single execution context. Part Two: Prefill.
Input first passes through template rendering and tokenization, then enters the model as fixed-size chunks. Each chunk reads previously committed state and atomically advances the frontier. Part Three: Decoding.
Ordinary decoding commits one token per round; speculative decoding can verify multiple candidates and commit a contiguous prefix. Regardless of how many candidates are accepted, the public output, KV cache, loop state, and counters must correspond to the same committed position; state must not be left half-updated.

Part Four: Long Context.
As context grows, fixed weight reads and continuously growing attention-cache reads jointly determine latency. Reports should provide absolute speed, relative retention, and the actual prompt token count, and should record cache format, maximum capacity, sampler, and graph execution state.

Stable inputs must be saved as the exact message files that were sent, with their source and token count recorded. Formal runs must not download web pages on the fly, select questions at random, or remove slower samples. Every number must be traceable to a specific model, command, input, and service logs.
