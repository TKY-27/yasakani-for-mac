Median: computing the exact median requires storing all values. Since there's a bounded memory requirement, I have to be careful. Options:
1. Cap the number of records retained for the median (e.g., maintain an in-order structure with a cap, or use the P² algorithm or a quantile sketch).
2. Use a "bounded sorted insertion" approach: keep a window of the last N values (a circular buffer) and compute the median over that window. This changes the semantics.
3. Use histogram buckets — approximate.

The requirement says "bounded memory" and "compute mean/median/sample standard deviation". Clean approach: exact mean and sample std via streaming moments (count, sum, sumSq — actually better: use Welford's online algorithm for numerical stability — Welford gives mean and M2 (sum of squared deviations); sample variance = M2/(n-1)). Exact median needs all data. Implement the median using a **capped order statistic**: keep up to `medianCapacity` (configurable, e.g., default 4096) samples per group in a sorted array maintained by insertion; once full, replace using a reservoir-sampling strategy (Vitter's algorithm) so that every sample beyond the capacity has a probability capacity/n of being included, then compute the median of the retained reservoir and mark it as approximate. This is a defensible engineering choice: bounded memory with a statistically unbiased reservoir; mean and std remain exact and streaming.

Or simpler: use insertion into a sorted array, and once we exceed the cap, randomly discard one (reservoir). Reservoir sampling on an array: when the count of seen elements exceeds capacity, generate random j ∈ [0, n); if j < capacity, replace element j and re-sort (or maintain the sorted invariant via binary insertion and deletion). Maintaining a sorted array with insertion/deletion is fine if O(capacity) per op, and if the capacity is bounded (e.g., 4096) that's fine, and for tests it's O(capacity) — no problem.
