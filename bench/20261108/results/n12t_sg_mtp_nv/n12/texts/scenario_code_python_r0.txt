"Deterministic" also means no timing-based behavior — jobs run in a fixed order. **Determinism:**
- Scheduler: deterministic topological order; ready set is sorted by (stable declaration order index, id). Actually, tie-breaking by declaration order is most deterministic given a manifest. But the lexicographic order of IDs is also deterministic. Let's use a priority queue of (ready_time?? no—) Let's keep it: use `heapq` with (seq_index, job_id) where seq_index is declaration order. When dependencies complete, the job becomes ready with its declaration index. This gives manifest-order execution when parallelism allows.
- Worker model: `max_concurrent` CPU jobs; GPU jobs are additionally serialized with a semaphore of 1. To keep it deterministic, GPU jobs are... hmm, if a GPU job is ready while a CPU job is running, which one starts next? With a general worker pool, a CPU job might grab a worker while the GPU job is waiting — that's fine; still deterministic under a fixed schedule? Under async, timing can interleave differently... strictly speaking, any async scheduling can vary. Let's make it a single scheduler task that:
  - Maintains a heap of ready jobs.
  - When capacity allows (workers < max_workers) and the head is a CPU job or the GPU semaphore is free, pop it; if the head is a GPU job with GPU locked, peek the next non-GPU job? This gets complex.

Simpler deterministic model: a single dispatcher loop:

```
while not all_done:
    if pending_gpu_job_ready and gpu_free and slot_free: start gpu job
    else if any_ready and slot_free: start the lowest (idx) ready job
    await next completion event or state change
```

Priority: GPU jobs take priority when free? Or strictly FIFO by index? Let's be strict: FIFO by declaration order, but the dispatcher only starts a job when its resource (a slot, and GPU semaphore if GPU) is available; if the head job is blocked on the GPU, allow starting a lower-priority non-GPU ready job (work-conserving). This is deterministic given a fixed completion order, and completion order is deterministic for a deterministic test. Good enough, and we'll document the policy.

The simplest, most robust implementation:

```python
async def dispatch(self):
    while self.remaining:
        ready = [j for j in self.remaining if all deps done]
        # pick the first ready job with resources
        picked = None
        for j in ready (sorted by idx):
            needs = slot always; gpu if j.gpu
            if self.slots_free and (not j.gpu or self.gpu_free):
                picked = j; break
        if picked is None:
            # wait for any in-flight to finish (wait FIRST in completion order? no—wait for any)
            await self.wait_any_done()
            continue
        start picked
```

Wait for any done: use `asyncio.wait(return_when=FIRST_COMPLETED)` on the set of running tasks, or an asyncio.Event set on each completion. Let's use a condition-like loop: gather running tasks; `done, _ = await asyncio.wait(running, return_when=FIRST_COMPLETED)`. Careful: a task finishing triggers state writes and events. Good.

This is O(n^2) but fine for manifest-scale.

**Resume:** on startup, load state; for each job in the manifest:
- If status is succeeded → mark done (resumed), emit `job_resumed` event with skipped true.
- If status is failed and attempts >= max_attempts → permanently failed; if it's a dependency target... it's failed anyway.
- Otherwise, pending.

If all jobs are succeeded → emit run_started + run_finished (succeeded, resumed=true) and exit 0.

Also, `failed` jobs below max_attempts → re-run on resume (retry after fix). Documented.

**CLI exit codes:**
- 0: all succeeded
- 1: one or more jobs failed
- 130: cancelled (SIGINT)
- 2: manifest invalid / config error
